# COFA 시험 실행 가이드

이 저장소를 사용할 수 있는 허용된 구현 단계의 운영안이다. 최신 시험 안내와 제공 환경이 우선한다. 아래 시간 배분은 180분을 가정한 권장안이며 공식 절차·배점이 아니다. 기존 [규칙 요약](../skills/cofa-delivery/references/exam-boundaries.md)의 날짜·마감 시각은 과거 안내 기록이므로 재응시 일정으로 사용하지 않는다. 전체 종료 시각과 후속 단계에 필요한 시간은 최신 안내에서 따로 확인한다.

목표는 도구 수가 아니라 **요구사항에 맞게 동작하고, 검증했으며, 본인이 설명할 수 있는 결과물**이다.

## 1. 준비할 Skill과 기본 구성

기존 사전체험에서 성공한 COFA의 추가 방식으로 공개 저장소 `SubJeeLee/skills`의 `skills/cofa-delivery` **폴더 전체**를 등록한다. `SKILL.md` 한 파일만 가져오면 참조·양식·스크립트가 빠진다. 설치만으로 세션이 시작되지는 않는다.

| 구성 | 언제 사용하나 |
| --- | --- |
| `cofa-delivery` | 메인 진입점. 명세 연결, 병렬 작업 준비·배정, 구현·검증·통합 |
| `cofa-requirements-interview`·`cofa-requirements-review` | 함께 등록됐다면 담당자 질문과 원문 대조에 사용. 없으면 cofa-delivery의 기본 참조로 진행 |
| `cofa-architecture-tour` | 코드 흐름을 HTML로 이해할 필요가 있을 때 추가. 없으면 파일·함수 근거를 담은 짧은 텍스트로 설명 |

Ponytail과 frontend-design·Emil의 원문 및 적용 기준은 cofa-delivery 안에 포함돼 있다. 기본 과제 수행에 별도 등록이나 MCP는 필수가 아니다. visual-explainer는 선택 사항이다. **Spec Kit 자체는 이 저장소에 포함되거나 자동 설치되지 않는다.** 실제 환경에 제공·등록됐다면 그 설치본의 절차를 사용하고, 없으면 간결한 기준 명세·계획·작업 목록으로 진행한다.

처음에는 아래 3개 탭이면 충분하다. 보조 세션이 실제로 지원되지 않으면 메인에서 순차 진행한다.

| 탭 | 역할 |
| --- | --- |
| Bash A | 제공 Codex의 메인 세션. 요구·구현·배정·통합 관리 |
| Bash B | 별도 제공 Codex의 보조 세션. 배정된 검토 또는 독립 구현 |
| Bash C | 필요할 때 개발 서버·로그·검사. AI 세션으로 세지 않음 |

터미널의 여러 탭, 공유 파일 접근, 독립 Codex의 동시 실행은 서로 다른 확인 항목이다. 같은 `pwd`만 보지 말고 메인이 만든 같은 파일의 내용을 보조에서 실제로 읽는다. 제공 런처가 있다면 그 방법을 사용하고, 지원되지 않는 동시 실행을 설정·별도 인증으로 우회하지 않는다.

## 2. Bash A에서 첫 요청

제공 작업 공간의 실제 과제 README와 지침을 먼저 확인한다. 과제 루트와 Skill 설치 경로를 혼동하지 않는다. 아래는 **Codex에 보낼 프롬프트**이며 셸 명령이 아니다.

```text
cofa-delivery를 메인 역할로 적용해줘.
실제 과제 루트의 README·제공 자료·기존 지침과 코드를 먼저 읽어줘.

해결할 문제, 사용자, 필수 기능·제출물, 데이터와 제약,
결과를 바꾸는 미확인 조건, 첫 핵심 사용자 흐름을 짧게 정리해줘.
자료로 확인되는 내용은 먼저 확인하고 담당자에게 물을 질문만 추려줘.

Spec Kit이 제공돼 있으면 기존 명세·계획·작업 목록을 기준으로 삼고,
없으면 설치를 기다리지 말고 같은 기준의 간결한 문서로 진행해줘.
초기 분석·계획은 20~30분을 권장 목표로 조정하되 필수 조건은 생략하지 마.

공유 파일 기반 병렬 준비를 진행하고 첫 실제 작업 요청을 작성해줘.
입력 경로·기준 버전·담당 세션·수정 파일·완료 기준·보고서를 채운 뒤
내가 보조 Bash에 전달할 시작 프롬프트를 알려줘.
그동안 메인은 충돌하지 않는 작업을 계속해줘.

기능과 검증을 우선하고 디자인은 현재 적용 기준에 맞춰 후순위로 유지해줘.
실제 변경·검사·결정 이유와 남은 한계를 기록하고,
첫 흐름이 동작하면 내가 실제 코드의 데이터 흐름을 설명할 수 있게 도와줘.
```

Skill 호출이 인식되지 않으면 실제 설치된 `cofa-delivery/SKILL.md` 경로를 명시해서 읽힌다. 경로나 명령을 임의로 만들지 않는다.

메인이 준비해야 하는 것은 기존 기준 문서의 실제 경로, `.cofa/coordination.md`, 완성한 첫 요청과 보조 시작 프롬프트다. 초기화 스크립트는 빈 양식을 준비할 뿐이며, `.cofa/tasks/R01.md`를 실제 자료에 맞게 채우는 것은 메인이다. 요청과 담당·수정 범위가 비어 있으면 보조를 시작하지 않는다.

## 3. 문제 정의를 구현으로 전환

질문은 답변에 따라 기능·데이터·업무 규칙·검사 결과가 달라지는 것만 우선한다. 예를 들어 안내·조회와 자동 추천·배정의 책임 범위, 데이터의 의미, 선택 기준, 실패 시 기대 동작이 해당한다. 패키지·파일명 같은 내부 기술 선택을 업무 담당자에게 넘기지 않는다.

우측 패널의 업무 담당자에게는 선별한 질문을 직접 전달하고 실제 답변을 메인에 돌려준다. 업무 규칙은 원문과, 수치·데이터 정의는 제공 파일과 대조한다. 답변의 추측이나 효과 예측을 검증된 사실로 바꾸지 않는다. 원문과 충돌하면 차이를 드러내고 필요한 조건을 재확인한다. 플랫폼 사용·저장·제출 질문은 Cofa Helper 등 제공 도움말로 구분한다.

첫 구현을 시작할 기준은 다음과 같다.

- 사용자가 수행할 가장 중요한 흐름 하나가 정해졌다.
- 그 흐름의 입력·출력과 중요한 업무 규칙이 정해졌다.
- 성공을 실제로 확인할 방법과 필수 제출물이 정해졌다.
- 미확인 조건은 관련 구현을 막는 것과 가정을 명시하고 진행할 수 있는 것으로 나뉜다.

문서의 모든 세부가 끝날 때까지 기다리지 않는다. 한 조건이 막혀도 그와 무관한 실행 환경 확인·기존 코드 탐색·독립 구현은 진행한다. Spec Kit 문서를 다른 계획 도구로 다시 작성하거나 여러 명세를 경쟁시키지 않는다.

## 4. Bash B에서 배정 작업 시작

메인이 준비한 실제 프로젝트 폴더를 Bash B에서 열고, 같은 배정표 내용을 읽을 수 있는지 확인한다. 제공 방식으로 메인과 별개 Codex 세션을 시작한다. 첫 세션을 배정된 유일한 담당으로 지정한 뒤 다음처럼 요청한다.

```text
이 세션은 메인이 배정한 첫 작업의 유일한 보조 담당이야.
.cofa/prompts/worker.md를 읽고 지정된 작업만 수행해줘.
```

메인이 해당 프롬프트의 실제 작업 경로와 담당 별칭을 채운 상태여야 한다. 다른 회차를 시작할 때는 기존 `R01`을 그대로 다시 실행하지 않는다. 이미 running인 작업의 재개라면 같은 담당 세션인지 실제 정보 또는 사용자 확인으로 구분한다.

보조가 시작하면 메인에 알려 배정표를 갱신한다.

```text
배정한 보조 세션이 해당 요청으로 작업을 시작했어.
배정표에 실제 시작 상태를 반영하고 독립적인 구현을 계속해줘.
```

처음에는 보조에 원문 대비 명세의 누락·근거 없는 가정을 맡기는 편이 좋다. 인터페이스와 파일 경계가 확정되면 독립 함수·모듈 구현을 맡길 수 있다. 첫 흐름 이후에는 검증이나 코드 추적으로 역할을 바꿀 수 있으며, 메인이 새 회차와 범위를 지정해야 한다.

공유 타입·API 계약·패키지·잠금 파일·공유 설정·기준 명세는 메인이 관리한다. 같은 파일의 수정 책임자는 한 명이다. FE·BE라는 이름만으로 독립이라고 보지 않는다. 공유 DB·서버 상태를 바꾸는 검사도 충돌 여부를 확인한다. 별도 탭이 기술적인 파일 격리·잠금이나 권한 제한을 제공하지는 않는다.

## 5. 보고서 회수와 다음 작업

보조가 작업 ID·회차·최종 보고서 경로를 알려주면 그 실제 경로를 메인에 전달한다.

```text
보조가 알려준 최종 보고서는 다음 경로야: [실제 보고서 경로]
해당 작업·회차·입력 버전과 변경 파일을 확인하고,
원문·현재 diff·실제 검사 결과를 대조해 채택·수정·보류를 판단해줘.
필요한 통합 검사를 수행하고 배정표와 기존 작업 목록을 갱신해줘.
```

보고서 파일이 있다는 이유로 성공 처리하지 않는다. 작성 중 파일·이전 회차·실패·차단 상태를 구분한다. 공유 폴더의 수정은 이미 현재 코드에 보이므로 별도 브랜치처럼 patch를 중복 적용하지 않는다.

다음 배정은 실제로 독립된 일이 있을 때만 만든다. 보조가 멈추거나 담당자가 바뀌면 기존 쓰기 작업의 중단을 확인한 뒤 새 회차를 지정한다. 파일 저장은 세션 간 알림이 아니므로 사람이 결과 경로를 전달하는 방식을 기본으로 한다.

## 6. 권장 시간 배분

| 경과 | 메인의 목표 | 보조에 맡길 후보 |
| --- | --- | --- |
| 0~10분 | 안내·README·환경·제출물·Skill 확인 | 세션과 공유 파일 지원 확인 |
| 10~30분 | 중요한 질문, 최소 명세·계약, 첫 실행 계획 | 원문과 기준 명세 대조 |
| 30~80분 | 핵심 사용자 흐름 하나를 끝까지 실행 | 계약이 정해진 독립 구현 |
| 80~125분 | 나머지 필수 기능, 오류·경계 처리 | 완성된 흐름 검증·코드 추적 |
| 125~150분 | 실제 검사와 오류 수정 | 요구별 근거와 미검증 범위 대조 |
| 150~170분 | 최종 검증, 실행 문서, 본인 이해 | 최종 코드 기준 설명·기록 확인 |
| 170~180분 | 저장·필수 파일·제출 미리보기·제출 | 새 코드 수정 배정 종료 |

디자인 시간을 따로 선점하지 않는다. 첫 UI는 frontend-design의 최소 시각 기준만 적용해 기능을 구현하고, Emil·animate는 필수 기능과 주요 검증 완료 후 제출 시간을 남길 수 있을 때만 선택한다. 시간이 부족하면 생략한다. 표의 다음 구간에 들어갔다고 미완성 기능을 완료 처리하지 않는다.

## 7. 구현 중 본인 이해도 확인

첫 사용자 흐름 완성 후와 핵심 로직 변경 후 대표 입력 하나를 코드에서 추적한다. 아직 설치하지 않은 HTML 도구나 전체 구조도 제작 때문에 구현을 멈추지 않는다. 우선 텍스트로 설명할 수 있으면 된다.

```text
현재 완성된 핵심 사용자 동작 하나를 실제 코드로 추적해줘.
입력 → 요청 → 검증 → 업무 처리 → 조회·저장 → 응답·화면의 순서를
실제 파일·함수와 연결하고 없는 단계는 생략해줘.
중요한 분기·선택 기준과 실패 경로 하나도 함께 설명해줘.
코드에서 확인한 사실과 실행으로 검증한 사실을 구분해줘.
이후 내가 문서를 보지 않고 직접 설명해볼게.
```

사람은 데이터 출처, 중요한 선택 이유, 실패 시 동작과 확인한 범위를 짧게 말해본다. 설명이 막히는 부분만 다시 코드와 대조한다. AI가 대신 설명했다는 사실을 본인이 이해·검토한 증거로 쓰지 않는다.

Docker가 필수라면 Dockerfile 작성, 이미지 빌드, 컨테이너 기동, 포트로 앱 요청 확인을 구분해 이해한다. 파일만 작성했으면 빌드·실행 성공이라 말하지 않는다. 외부 배포가 요구되지 않았다면 임의로 추가하지 않는다.

## 8. 제출 전 실제 확인

새 작업 배정을 멈추고 진행 중인 쓰기 작업을 확인한다. 과제가 요구한 기존 검사·타입 검사·빌드·기능 시나리오 중 관련 항목을 실제로 수행한다.

- 원문 요구별 구현 위치와 실제 결과가 연결되는가?
- 핵심 정상 흐름, 잘못된 입력·실패·권한 등 관련 경계를 확인했는가?
- 저장이 필요한 기능은 성공 표시뿐 아니라 재조회 등 실제 상태를 확인했는가?
- 필요한 Docker 산출물·실행 방법·환경변수·제공 경로가 정확한가?
- README와 제출 문서는 최종 코드와 일치하며 미검증·미구현을 구분하는가?
- 플랫폼의 실제 저장·제출 화면과 최신 안내의 필수 파일을 확인했는가?

에이전트의 '완료' 메시지, 빌드 성공, 실제 요구사항 충족은 각각 확인한다. 검사하지 않은 결과나 사람의 판단·성과를 만들어 기록하지 않는다.

## 9. 후속 서술형 준비와 전환

아래는 구현 중 또는 시험 전 연습할 주제이며 실제 출제 예측이나 미리 작성한 답안이 아니다.

1. 어떤 문제를 우선했고 왜 그 기능부터 구현했는가?
2. 입력이 어떤 파일·함수를 거쳐 결과가 되는가?
3. 알고리즘·구조·저장 방식을 왜 선택했고 어떤 대안을 포기했는가?
4. 담당자 답변이나 AI 제안에서 무엇을 채택·수정·보류했고 어떻게 확인했는가?
5. 실제 오류를 어떻게 재현·수정·재검증했는가?
6. 남은 한계와 다음에 확인할 부분은 무엇인가?

답변은 질문의 결론 → 실제 구현·행동 → 선택 이유 → 확인한 증거 → 한계 순서로 직접 구성한다. 코드나 질문의 전제가 기억과 다르면 차이를 밝히고, 기억하지 못하는 함수명·명령·수치를 추측하지 않는다. 자세한 연습은 [서술형 준비](../skills/cofa-delivery/references/written-practice.md)를 따른다.

AI 금지 후속 단계가 시작되면 AI에 답안 작성·분석·검토를 요청하지 않는다. 기존 docs·코드의 열람 가능 여부도 최신 안내에서 확인하며 볼 수 있다고 전제하고 준비하지 않는다.

## 10. 막혔을 때의 최소 대안

| 상황 | 대응 |
| --- | --- |
| Skill 등록·선택이 인식되지 않음 | 허용된 설치 경로의 SKILL.md를 직접 읽힘. 폴더 리소스 존재 확인 |
| Spec Kit이 제공되지 않음 | 기준 요구·완료 조건·기술 계약·작업을 간결한 기존 문서로 유지 |
| 두 Codex가 동시 실행되지 않음 | 메인에서 같은 요청을 순차 수행. 독립 검토라고 기록하지 않음 |
| 파일을 공유하지 못함 | 제공 환경 안의 허용된 텍스트 전달 방법 사용. 불가하면 순차 진행 |
| MCP 연결에 시간이 듦 | 필요한 기능인지 판단하고 기본 파일 탐색·셸로 진행. 시작의 필수 조건으로 두지 않음 |
| 플랫폼·서버 장애 | 발생 시각·단계·오류를 남기고 제공 신고·도움말 이용. 타이머 정지를 추정하지 않음 |

MCP가 필요한 경우에만 [COFA JSON 연결 안내](../skills/cofa-delivery/references/mcp-json.md)를 따른다. JSON 저장·도구 검색·호출 성공은 서로 다른 상태다. 브라우저 자동화 허용 여부는 별개이므로 기본 실행에 포함하지 않는다.
