# 병렬 작업 배정표

메인 Codex만 이 파일을 수정한다. 양식 생성은 세션 실행·작업 완료의 증거가 아니다. 역할 이름으로 파일 접근 권한이 기술적으로 제한되지는 않는다.

## 기준 자료

- 과제 원문·README 실제 경로: 미지정
- Spec Kit 기준 명세 실제 경로: 미지정
- 기술 계획 실제 경로: 미지정
- 기준 작업 목록 실제 경로: 미지정
- 실제 담당자 답변 기록 경로: 해당 시 지정
- 프로젝트 절대경로: {{PROJECT_ROOT}}

기존 문서가 있으면 연결한다. 이 배정표 때문에 별도 명세·작업 목록을 복제하지 않는다. 기준 경로가 정해지기 전 보조 세션에 구현을 배정하지 않는다.

## 실제 환경

| 확인 항목 | 상태 | 직접 확인한 근거 |
| --- | --- | --- |
| 별도 Bash에서 같은 확인 파일 읽기 | 미확인 | |
| 제공 Codex의 독립 세션 실행 | 미확인 | |
| 두 세션의 동시 실행 | 미확인 | |

미확인 상태를 성공으로 바꾸지 않는다. 지원되지 않으면 메인이 같은 작업을 순차 수행한다. 개인 로그인·별도 모델·설정 변경으로 우회하지 않는다.

## 작업 배정

| 작업 ID·회차 | 기준 작업 ID | 담당 세션 | 상태 | 선행 조건 | 수정 가능한 파일 | 요청 경로 | 보고서 경로 |
| --- | --- | --- | --- | --- | --- | --- | --- |

실행 상태의 유일한 기준은 이 배정표다. 상태는 draft → ready → running → reported → accepted로 구분하며 blocked·failed·cancelled도 사용한다. 요청의 '배정 준비: ready'는 고정된 요청이 완성됐다는 뜻이며 실행 상태가 아니다.

ready 작업에는 유일한 담당 세션 별칭을 지정하고, 사용자에게 전달할 시작 프롬프트에 같은 별칭과 작업 ID·회차를 넣는다. 실제 세션 ID가 제공되면 함께 기록하되 별칭을 실제 ID라고 쓰지 않는다. 사용자가 별도 Bash의 시작을 확인하면 메인이 running으로 바꾼다. 같은 요청을 여러 세션에 전달하지 않는다. running 재개는 같은 담당임이 확인될 때만 허용하고, 담당자가 바뀌면 기존 쓰기 중단을 확인한 뒤 새 회차를 사용한다. reported·accepted·cancelled 결과를 새 작업으로 실행하지 않는다.

파일 존재나 에이전트의 완료 주장만으로 accepted로 올리지 않는다. 이 절차는 운영상 소유권 확인이며 기술적인 세션 인증이나 파일 잠금을 제공하지 않는다.

## 수정 책임과 계약

- 메인: 기준 명세·계획·작업 목록, 공유 타입·API 계약, 패키지·잠금 파일, 공유 설정, 이 배정표와 작업 요청.
- 보조: 요청에 열거한 파일만. 디렉터리 단위라면 제외할 공유 파일과 재귀 범위를 명시한다.
- 서버 셸: 개발 서버와 지정 검사. AI 세션으로 세지 않는다.

동시 작업의 쓰기 경로가 겹치면 ready로 배정하지 않는다. 계약은 기준 계획의 실제 위치를 연결하고, 계약이 바뀌면 영향받는 작업을 보류·재배정한다. 공유 DB·서버 상태를 바꾸는 검사도 충돌 여부를 확인한다.

## 접수와 사람이 확인한 판단

| 작업·보고서 | 채택·수정·보류 | 원문·diff·검사 근거 | 통합 후 결과·남은 한계 | 사람이 실제 확인한 내용 |
| --- | --- | --- | --- | --- |

확인하지 않은 사람의 판단이나 검증 성공은 채워 넣지 않는다. 과제와 코드·작업 기록은 로컬 작업 공간에 두고 공개 저장소에 올리지 않는다.
