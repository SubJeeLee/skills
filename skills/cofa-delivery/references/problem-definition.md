# 문제 정의와 요구사항

## 페르소나를 책임으로 정의

권장 역할은 '업무 요구를 실행 가능한 소프트웨어로 구체화하는 개발 파트너'다. 연차·권위 선언으로 정확성을 가정하지 않는다. 사람은 목표·우선순위를 결정하고, 에이전트는 근거 탐색·설계·구현·검증을 수행한다.

## 확인 순서

1. 과제 원문·README·기존 지침·현재 구현을 확인한다.
2. 사용자, 문제, 필수 결과물, 제약, 기존 동작을 분리한다.
3. 미확인 사항 중 결과·권한·데이터 의미·수용 기준을 바꾸는 조건을 질문한다.
4. 답변을 반영해 사실·가정·범위 밖을 표시한다.
5. 사람과 핵심 사용자 흐름·우선순위를 확인한다.

질문은 답에 따라 무엇이 달라지는지 설명한다. 자료에 답이 있거나 작은 구현 선택인 경우 질문을 늘리지 않는다. 중요 조건이 확인되지 않았으면 임의 기능으로 덮지 않는다.

담당자에게 직접 보낼 질문 목록과 답변 반영표가 필요하고 해당 폴더가 제공돼 있으면 [담당자 질문 Skill](../../cofa-requirements-interview/SKILL.md)을 적용한다. 질문 생성과 실제 담당자 메시지 전송을 구분한다.

## 질문 예시

| 확인할 조건 | 설계에 미치는 영향 |
| --- | --- |
| 누가 등록·조회·수정하는가? | 사용자 흐름과 권한 경계 |
| 담당자는 어떻게 지정되는가? | 수동 선택·자동 규칙 여부 |
| 상태 변경의 허용 조건은? | 상태 전이와 검증 위치 |
| 실패·중복 요청을 어떻게 다루는가? | 오류 처리와 저장 일관성 |
| 가장 중요한 성공 장면은? | 구현 우선순위 |
| 제공 데이터·환경만으로 가능한가? | 외부 의존성·모의 구현의 허용 범위 |

## 좋은 완료 기준

'편리한 관리' 대신 '유효한 신고가 저장되고 재조회에서 같은 값으로 보인다'처럼 관찰 가능한 동작을 쓴다. '생산성 30% 증가' 등 자료에 없는 기준선·효과를 만들지 않는다.

요구사항에는 ID, 원문 근거, 우선순위, 기대 동작, 검증 방법을 연결한다. 필수 조건을 시간 부족만으로 삭제하지 않는다. 구현 불가능한 부분은 한계로 분리하고 합의 가능한 경우에만 범위를 조정한다.
