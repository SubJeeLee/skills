# 여러 Bash에서 Codex 역할 나누기

이 문서는 터미널 탭을 직접 여는 제공 환경에서 작업을 나누는 운영안이다. 여러 Bash 탭이 존재한다고 여러 Codex 세션·공유 파일·사용 한도까지 확인된 것은 아니다. 제공 실행 안내와 실제 파일을 확인하고 지원되는 범위에서 사용한다. 개인 로그인·별도 모델 연결·관리 설정 변경 없이 제공 Codex만 사용한다.

## 세 가지 방식을 구분

| 방식 | 시작과 결과 전달 | 기록할 표현 |
| --- | --- | --- |
| 별도 Bash의 독립 Codex 세션 | 사람이 각 세션을 시작하고 문서 경로·결과를 전달 | 수동 분리 CLI 세션. 이 문서의 주 운영안 |
| Codex 네이티브 서브에이전트 | 실제 지원될 때 메인이 위임 도구로 생성·취합 | 실제 도구와 세션이 확인된 서브에이전트 |
| 한 세션의 순차 역할 전환 | 같은 대화에서 검토 관점을 변경 | 순차 검토. 독립 세션 검증으로 표현하지 않음 |

별도 Bash 세션을 운영상 검토 담당·보조 에이전트라고 부를 수 있으나 네이티브 spawn이나 자동 오케스트레이션을 사용했다고 기록하지 않는다. 독립 대화여도 같은 모델의 판단 오류가 반복될 수 있으므로 원문과 증거를 확인한다.

## 최소 구성

| 탭 | 용도 | 쓰기 범위 |
| --- | --- | --- |
| Bash A | 메인 Codex: 문제 정의·질문 정리·구현·통합 | 기준 명세, 제품 코드·공유 설정과 작업 기록 |
| Bash B | 검토 Codex: 문제 정의와 인수 조건 대조 | 제품·기준 명세 수정 금지. 명시적으로 맡긴 회차별 검토 보고서만 작성 |
| Bash C(필요할 때) | 개발 서버·로그 또는 검사 명령 | 서버 프로세스나 지정 검사. AI 세션이라고 간주하지 않음 |

처음부터 역할별 탭을 모두 열지 않는다. 메인과 검토가 먼저이며 검토가 끝나면 같은 보조 세션을 종료하거나 명확히 재지정한다. 문맥을 넘겨 다시 쓰는 경우 새 역할·읽을 입력·버전을 명시한다. 더 독립적인 재검토가 필요하면 지원되는 새 세션을 사용한다.

## 시작과 파일 공유 확인

1. Bash A에서 제공 작업 디렉터리와 README, 기존 지침, Codex 실행 방법을 확인한다.
2. 기준 명세와 실제 담당자 답변을 문서로 남긴다. 개인 PC 파일이나 외부 메신저로 전달하지 않는다.
3. Bash B를 열고 같은 기준 문서를 실제로 읽을 수 있는지 확인한다. `pwd`가 같다는 사실만으로 같은 파일시스템이라고 단정하지 않는다. 기존 문서 경로·내용을 대조한다.
4. 제공 안내의 명령으로 별도 Codex를 실행한다. 일반 셸의 `codex` 실행은 예시이며 제공 런처가 있으면 그 방법을 따른다. 대화 식별자가 제공되면 메인과 다른 세션인지 확인하고, 같은 대화를 재개한 상태를 독립 검토라고 기록하지 않는다. 동시 실행이 막히면 별도 인증·연결 변경으로 우회하지 않는다.
5. 원문 경로, 기준 명세, 답변 기록, 검토 버전과 반환 위치를 명시한다. 새 세션은 메인 대화를 자동으로 안다고 가정하지 않는다. 같은 프로젝트 지침을 자동으로 읽었는지도 확인한다.

공유 파일에 접근할 수 없다면 제공 환경 안에서 허용된 텍스트 전달 방법을 사용한다. 그마저 불가능하면 메인 세션의 순차 검토로 전환하고 검증 방식을 정확히 기록한다.

## 검토 입력을 안정화

[검토 요청 양식](../assets/review-request.md)에 회차 ID, 관련 파일과 요구사항을 남긴다. 경로명은 예시이며 기존 과제 문서와 필수 제출 파일을 우선한다.

검토 중에는 대상 명세의 변경을 잠시 멈추고 메인은 독립된 환경 확인·기존 코드 탐색을 진행할 수 있다. 명세 변경이 불가피하면 해당 입력의 고정 스냅샷 또는 시작·종료 내용 해시를 사용하고 변경된 범위는 재검토한다. 커밋 SHA만으로 커밋하지 않은 문서까지 고정됐다고 보지 않는다.

검토 보고서는 회차마다 별도 경로를 배정한다. 두 세션이 같은 작업 기록이나 기준 명세를 동시에 편집하지 않는다. 예를 들어 메인이 요청 문서를 작성하고, 검토 담당은 자신의 보고서만 작성하며, 채택 결과는 메인이 기준 명세와 작업 기록에 반영한다.

## Bash A에 전달할 요청

```text
cofa-delivery를 적용하고 README와 실제 담당자 답변으로 기준 명세를 정리해줘.
초기에는 첫 사용자 흐름과 필수 조건, 중요한 가정만 정리해줘.

별도 Bash에서 문제 정의 검토 세션을 실행하려고 해.
검토할 원문·데이터 설명·담당자 답변·명세 경로와 버전을 정리하고,
보조 세션에 전달할 요청 문서를 기존 작업 공간에 작성해줘.
보조 세션에는 제품 코드와 기준 명세 수정 권한을 주지 말고,
해당 회차의 보고서 경로만 지정해줘.

검토 중에는 입력 명세를 바꾸지 않는 독립 작업을 진행해줘.
보고서가 도착했다고 추정하지 말고 내가 경로를 전달하면 읽어줘.
각 발견을 원문과 대조해 채택·재질문·보류 이유를 기록하고,
중요 결정이 확정되면 구현을 이어가줘.
```

## Bash B에 전달할 요청

```text
너는 제품 구현자가 아니라 문제 정의 검증 담당이야.
cofa-requirements-review Skill이 제공돼 있으면 읽고 적용해줘.
없으면 이 요청의 검토 범위 안에서 원문 대조를 수행해줘.

내가 지정한 검토 요청 문서에서 작업 ID, 실제 원문·명세·답변 경로,
기준 버전과 보고서 경로를 확인해줘. 이 경로를 먼저 전달받아야 해.
이전 Codex 세션 대화를 알고 있다고 가정하지 마.

README와 실제 담당자 답변을 먼저 읽고 기준 명세를 대조해줘.
근거 없는 가정, 필수 요구 누락, 데이터·업무 규칙 충돌,
관찰하기 어려운 인수 조건과 불필요하게 확대한 범위를 확인해줘.
발견마다 원문 근거와 명세 위치, 구현 영향, 최소 조치를 붙여줘.
관련 결정을 막는 항목과 진행 가능한 가정을 구분해줘.

제품 코드·기준 명세·공유 설정을 수정하거나 담당자에게 메시지를 보내지 마.
명시적으로 배정된 검토 보고서만 작성하고 결과 경로를 반환해줘.
검토 중 입력 버전이 바뀌면 어느 판단을 갱신해야 하는지 표시해줘.
자료가 부족하면 답변이나 숨은 조건을 만들어 채우지 마.
```

각 프롬프트에 실제 요청 문서 경로를 붙인 뒤 사용한다. 보고서를 작성했다는 응답만으로 완료라 하지 않고 Bash A에서 파일이 저장됐고 올바른 버전을 검토했는지 확인한다.

## 회수와 종료

검토 담당의 결과를 메인이 직접 읽고 원문 근거로 판단한다. 첫 검토는 5~10분을 권장 시작점으로 하며 중요한 충돌만 먼저 회수한다. 이는 공식 시간 제한이 아니다. 문서의 완벽함을 목표로 질문과 검토를 무한 반복하지 않는다.

지원 환경에서 실제로 진행 중인 세션과 서버를 확인하고, 중단·역할 교체는 사람이 해당 탭에서 수행하거나 제공된 제어 기능을 사용한다. 중단을 확인하기 전 동일 파일의 새 수정자를 투입하지 않는다. 보조 세션이 끝나도 개발 서버가 필요하면 별도로 유지한다.

이 운영안은 세션 생성·메시지 자동 중계·파일 잠금을 구현하지 않는다. MCP 설정과 독립 세션 실행 지원도 별개다. 실제 시험의 동시 실행 허용·자원·토큰 범위는 제공 환경에서 확인한다.
