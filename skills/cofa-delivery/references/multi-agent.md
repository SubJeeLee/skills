# 멀티 에이전트 운영과 기록

준비·리허설 또는 AI가 허용된 구현 단계에서만 사용한다. 목표는 독립적인 탐색과 검증을 분리하면서 하나의 요구사항과 구현 결과로 통합하는 것이다. 여러 하네스의 중복 설치나 많은 에이전트 실행을 목표로 삼지 않는다.

## 환경 확인과 시작 구성

현재 제공 Codex에 실제 서브에이전트 기능이 있는지 확인한다. 최신 일반 Codex의 기능이 COFA 설치본에도 있다고 추정하지 않는다. 지원되지 않으면 같은 세션에서 탐색 → 구현 → 검증 순서로 진행하고, 이를 독립 에이전트 검토라고 기록하지 않는다. 별도 모델·개인 인증을 연결하거나 관리 설정을 변경해 기능을 활성화하지 않는다.

권장 시작 구성은 메인 1개와 필요할 때 실행하는 보조 최대 2개다. 공식 제한이나 최적 성능을 보장하는 숫자는 아니다. 토큰, 응답 지연, CPU·RAM과 남은 시간에 따라 줄인다. 한 명의 개발자가 더 빠르게 끝낼 작은 작업은 분리하지 않는다.

| 역할 | 책임 | 수정 경계 | 종료 기준 |
| --- | --- | --- | --- |
| 사람 | 목표·우선순위 결정, 중요한 제안 확인, 결과 이해 | 본인의 판단을 AI가 했다고 대체 기록하지 않음 | 핵심 흐름·선택 이유·한계를 직접 설명 |
| 메인 | 요구사항 통합, 설계, 핵심 구현, 위임과 결과 통합 | 공통 타입·설정·공유 문서의 수정 조율 | 인수 조건과 실제 증거가 연결됨 |
| 탐색 담당 | 기존 코드·문서, 영향 범위와 누락 조건 조사 | 우선 파일 변경 없이 조사 | 근거 파일·불확실성·다음 제안을 요약 |
| 검증 담당 | 원문 요구와 코드·실행 결과 대조, 오류 재현 | 초기에는 제품 코드 수정 없이 확인; 테스트 작성 시 담당 경로 합의 | 실제 실패·검사 결과·미검증 범위 반환 |

탐색 담당이 끝나면 종료하고 검증 담당을 시작해도 된다. 설계 전에 구현부터 분산하지 않는다. 독립적인 탐색은 병렬로 수행하되, 같은 동작의 구현·검증 결과가 서로 의존하면 필요한 코드와 조건이 준비된 뒤 실행한다.

## 위임 계약

작업마다 다음을 짧게 전달한다. 긴 대화나 전체 로그 대신 기준 문서와 필요한 파일 위치를 지정한다.

- 작업 ID와 목적: 어떤 요구사항이나 위험을 다루는가.
- 입력: 원문 요구, 관련 코드·인터페이스, 필요한 업무 답변.
- 담당 범위: 수정 가능한 경로와 다른 담당자가 소유한 경로.
- 완료 조건: 관찰할 동작과 반환해야 할 근거.
- 제약: 기존 API·타입 계약, 허용 도구, 대기해야 할 선행 작업.
- 반환 내용: 변경 파일, 발견과 근거, 실행한 검사와 결과, 미검증 항목.

검증 담당에게는 원문 요구사항과 실제 코드를 제공한다. 구현자의 완료 요약만 보고 승인하지 않게 한다. 파일을 읽고 추정한 결과와 실행으로 관찰한 결과를 구분한다. 별도 에이전트의 검토도 정답을 보장하지 않으므로 메인이 근거를 확인한다.

## 파일 수정과 통합

1. 한 파일의 수정 책임자는 한 명으로 정한다. 공통 타입, 패키지·잠금 파일, 공유 설정은 메인이 조율한다.
2. 병렬 구현이 필요하면 먼저 API·데이터 형식·실패 처리와 담당 경로를 합의한다. 명목상 FE·BE 분리만으로 독립 작업이라고 보지 않는다.
3. 담당 범위를 벗어난 변경이 필요하면 메인에 영향과 이유를 전달한다. 다른 담당자의 변경을 되돌리거나 덮어쓰지 않는다.
4. 반환된 변경은 diff와 인수 조건으로 확인한다. 별도 브랜치·worktree를 썼다면 통합된 작업 공간에서 관련 검사를 다시 실행한다. 별도 체크아웃이 없는데 격리됐다고 가정하지 않는다.
5. 검증 실패는 재현 조건과 근거를 구현 담당에게 반환하고 수정 후 같은 조건과 관련 회귀를 확인한다. 실행 중인 쓰기 작업과 충돌할 검사는 통합 시점을 맞춘다.

테스트가 공유 DB·서버 상태를 바꾸면 읽기 전용 검토가 아니다. 격리 가능한 테스트 데이터·인스턴스를 쓰거나 순차 실행한다. 도구나 에이전트의 권한은 이름·역할 지시만으로 기술적으로 제한된다고 가정하지 않는다.

## 대기·충돌·범위 초과 대응

- 위임 응답을 기다리는 동안 메인은 독립된 작업을 진행한다. 같은 분석을 중복 수행하지 않는다.
- 담당자가 응답하지 않으면 상태를 한 번 확인하고, 남은 시간에 맞춰 취소·재위임·직접 수행 중 하나를 선택한다. 중단을 확인하기 전 같은 파일의 새 수정자를 투입하지 않는다.
- 충돌은 현재 변경을 보존하고 책임자를 정한 뒤 통합한다. 원인을 모른 채 변경을 초기화하지 않는다.
- 요구와 무관한 제안은 범위에서 제외하고 이유를 기록한다. 모든 제안을 반박하거나 실패 사례를 일부러 만들 필요는 없다.
- 제출 전에는 진행 중인 위임·쓰기 작업과 서버 상태를 확인하고, 최종 코드 기준의 검사 결과와 미완료 범위를 정리한다.

## 기록과 본인 이해

[에이전트 작업 기록 템플릿](../assets/agent-worklog.md)을 기존 작업 기록에 필요한 만큼 통합한다. 별도 문서 생성은 필수가 아니며 과제의 제출 파일명이 우선이다. 원문 대화 전체 대신 작업 ID, 실제 세션·도구 식별자(제공될 때), 담당 경로와 증거 위치를 남긴다. 세션 ID를 만들거나 없는 도구 호출을 기록하지 않는다.

중요한 AI 제안에는 제안 내용 → 본인의 채택·수정·보류 판단 → 요구사항·시간 등 근거 → 실제 변경 → 검증 결과와 한계를 남긴다. 사람이 확인하지 않은 판단은 확인 대기로 표시한다. AI가 사람의 판단이나 검토 행위를 대신 꾸며 쓰지 않는다.

이 기록은 구현 단계의 추적과 시험 전 설명 연습을 위한 것이다. AI 금지 서술형에서 AI를 호출하거나 기록 열람이 허용됐다고 가정하지 않는다. 사람은 구현 중 핵심 데이터 흐름과 선택 이유를 직접 설명해본다.

## 시작 요청 예시

```text
cofa-delivery의 멀티 에이전트 운영 참조를 적용해줘.
현재 세션이 실제 서브에이전트를 지원하는지 먼저 확인하고,
지원되지 않으면 설정을 바꾸지 말고 같은 세션에서 순차 진행해줘.

README와 기존 지침을 기준으로 첫 핵심 사용자 흐름을 정리해줘.
독립된 코드 탐색이 필요하면 탐색 담당에게 파일 변경 없이 위임하고,
메인은 요구사항과 설계를 정리한 뒤 구현을 진행해줘.
구현이 준비되면 검증 담당에게 원래 요구와 실제 코드를 전달해
완료 조건별 검증을 요청해줘.

각 위임에 작업 ID, 담당 경로, 완료 조건과 반환할 증거를 지정해줘.
공유 파일의 동시 수정을 피하고 변경을 통합한 뒤 검사를 확인해줘.
실제 위임과 결과, 내가 채택하거나 조정한 판단을 기존 작업 기록에 남겨줘.
내가 확인하지 않은 내용은 사람 검토 완료로 기록하지 마.
```

근거: [공식 Codex Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents). 2026-10-30 확인. 역할·동시 실행 수·기록 양식은 이 저장소의 권장안이며 COFA 지원·시험 허가나 성능 보장이 아니다.
