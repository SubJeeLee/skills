# Ponytail을 적용하는 구현 기준

코드를 작성·수정하거나 디버깅할 때 이 프로필을 먼저 읽고 [포함된 원문](ponytail/upstream.md)의 `full` 원칙을 적용한다. 원문 파일은 별도 Skill을 찾아 설치하지 않고 읽을 수 있다. 원문의 전체 세션 적용·짧은 응답·최소 버전 지침은 아래 과제 범위와 기록 기준 안에서 해석한다. 요구사항 질문·확정 자체를 생략하거나 다시 시작하는 용도로 쓰지 않는다.

## 적용 순서

1. 확정된 필수 요구와 인수 조건, 배정된 파일·입출력 계약을 먼저 확인한다.
2. 기존 코드의 컴포넌트·함수·패턴을 찾고 같은 방식으로 재사용한다.
3. 프로젝트의 기존 구현을 우선하고, 적절한 표준 기능과 설치된 의존성을 활용한다. 작은 기능 때문에 새 의존성·래퍼·설정·확장 계층을 추가하지 않는다.
4. 요구를 끝까지 충족하는 읽기 쉬운 최소 변경을 만든다. 줄 수를 줄이기 위해 이해하기 어려운 표현을 쓰거나 호출부·실패 처리를 누락하지 않는다.
5. 중요한 신규 로직과 변경된 동작에는 필요한 작은 검사·기존 테스트를 실행하고 실제 결과와 미검증 범위를 남긴다.

## 과제·병렬 작업과 연결

- Spec Kit은 명세·계획·작업의 기준이다. Ponytail은 구현 선택에 적용하며 기준 문서를 대체하지 않는다. 확정 요구를 다시 논쟁하는 `ultra`를 기본으로 쓰지 않는다.
- 원문이 요구한 인증·저장·Docker 등 필수 동작과 입력 검증·오류 처리·보안·접근성을 축소하지 않는다. 의존성을 줄인다는 이유로 기존의 검증된 인증·보안 기능을 직접 다시 만들지 않는다.
- 보조는 호출부를 확인하되 배정받은 파일만 수정한다. 공통 코드에 원인이 있어도 메인에게 근거와 필요한 변경을 반환한다. 새 작업자를 만들거나 기존 소유권을 재배정하지 않는다.
- 결정 이유, 실제 검사 결과·한계와 요청된 데이터 흐름·구현 설명은 완료에 필요한 산출물이다. 짧은 응답 규칙 때문에 이를 삭제하거나 검증 완료를 꾸며 쓰지 않는다.
- 코드 투어·검토에서 원문에 없는 기능을 필수로 확대하지 않고, 실제 관련 근거만 확인한다. 새 전체 감사 절차나 추가 계획 하네스를 시작하지 않는다.

메인은 구현을 시작할 때 적용하고, 보조에는 작업 요청과 시작 프롬프트에 이 프로필을 읽도록 명시한다. 각 세션은 서로의 모드나 대화를 자동 공유하지 않는다. 이전 작업 폴더를 재개하면 생성된 프롬프트는 초기화 도구가 덮어쓰지 않으므로 메인이 필요한 원칙을 직접 반영한다. 진행 중 작업 요청은 조용히 고치지 않고 기존 재개·회차 규칙을 따른다.

이 폴더는 원문 Skill과 라이선스만 포함한다. 플러그인·훅·계기판·별도 명령은 설치하지 않으며 `/ponytail` 명령이 제공된다고 가정하지 않는다. 자연어로 full 원칙 적용을 요청할 수 있다. 실제 시간·비용 개선은 COFA에서 측정하지 않았다.
