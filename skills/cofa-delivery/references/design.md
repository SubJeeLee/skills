# 설계의 범위와 판단 기준

## 설계 전에 확인

설치된 런타임·패키지 관리 도구·기존 코드·실행 명령·검사 명령을 먼저 확인한다. React, Next.js, Python, DB 또는 OpenAI API 제공 여부를 추정하지 않는다. 개발에 Codex를 쓰는 것과 앱이 AI 기능을 제공하는 것은 별개다.

## 구현을 시작할 수 있는 설계

- 핵심 사용자 흐름: 입력 → 검증 → 처리 → 저장 → 출력·재조회.
- 필요한 데이터와 식별자, 상태·전이 규칙.
- 화면·API·도메인 로직·저장소 사이의 책임과 인터페이스.
- 실패·누락·중복·권한 문제 중 과제에 관련된 처리.
- 요구사항별 검사 방법과 중요한 가정.
- 첫 실행 가능한 범위와 나머지 필수 기능의 구현 순서.

문서 분량보다 추측해야 하는 중요한 결정이 줄었는지 판단한다. 여러 계층·새 프레임워크·마이크로서비스는 필요가 확인된 경우에만 도입한다.

## 중요한 선택 기록

선택, 이유, 대안, 포기한 점, 확인한 근거를 짧게 기록한다. 예: '기존 실행 구조를 유지해 환경 재구성 비용을 줄인다. 제공 저장 방식의 동시 쓰기 한계는 별도로 기록한다.' 단, 실제 환경을 확인한 뒤 쓴다.

## AI 기능이 요구될 때

허용된 호출 경로·모델·데이터 범위·오류 처리 조건을 확인한다. 개인 키나 외부 모델을 연결하지 않는다. 모의 응답이면 모의임을 밝힌다. 계산·규정·허용 상태 등 결정적인 판정은 근거에 따라 재현 가능하게 구현하고, 모델 출력은 구조와 업무 조건을 검증한다.

## 설계 종료 조건

필수 흐름·업무 규칙·완료 기준과 첫 실행 방법이 정해졌으면 구현으로 넘어가 실제 결과로 설계를 검증한다. 분석 시간은 과제 위험에 맞춰 조정하며 문서 도구의 전체 절차를 의무화하지 않는다.
