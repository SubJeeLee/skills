# 검증과 오류 수정

## 요구사항과 증거 연결

요구사항별로 구현 위치, 검증 방법, 기대 결과, 실제 결과, 한계를 기록한다. 상태는 구현 여부와 별도로 '실행 확인', '실패', '읽기 검토만 수행', '미검증', '해당 없음'으로 구분한다.

## 검사 선택

기존 프로젝트에서 관련 테스트, 타입 검사, 린트, 빌드를 실제 명령에 맞춰 수행한다. 실행하지 않은 명령·통과 수·커버리지를 만들지 않는다. 모든 변경에서 전체 검사 반복을 강제하지 않고 위험과 변경 범위에 맞춘다. 중요한 수정 뒤에는 관련 검증을 다시 실행한다.

## 시나리오

- 정상 입력과 핵심 흐름.
- 필수값 누락, 잘못된 형식, 존재하지 않는 ID.
- 과제에 관련된 권한·상태 전이·중복·동시 처리.
- 저장 실패, 외부 의존성 실패, 재조회·재실행.
- 부분 실패를 성공으로 표시하는지.

화면 테스트는 규칙에 맞춰 직접 수행한다. Playwright Test 및 MCP·CLI의 허용 범위는 확인되지 않았다. headless·DOM 기반·CLI라는 이유만으로 Computer Use 제한의 예외라고 가정하지 않는다.

## 오류 처리 순서

1. 재현 조건과 실제 오류를 확인한다.
2. 최근 변경과 입력·처리·저장·출력 경계를 추적한다.
3. 원인 가설과 확인 근거를 적는다.
4. 최소 변경으로 수정한다.
5. 원래 재현 조건과 관련 회귀를 다시 확인한다.

동일 실패가 반복되면 가설·범위·구조를 다시 검토한다. 무한 재시도나 과도한 프로세스 실행을 피한다. 플랫폼 장애는 복구 가능한 사용자 영역만 점검하고 문제 신고로 대응한다.

## 완료 보고

'테스트 통과'와 '요구사항 충족', '로컬 빌드 성공'과 '대상 환경 동작'을 구분한다. 에이전트의 성공 보고를 diff·명령 결과·직접 확인과 대조한다. 남은 오류와 미검증 사항은 제출 문서에 정확히 남긴다.
