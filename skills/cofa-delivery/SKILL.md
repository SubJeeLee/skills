# COFA Delivery

실제 과제의 요구사항을 구현과 검증까지 연결한다. 사용자가 직접 목표·우선순위를 결정하고 코드와 결과를 이해할 수 있게 돕는다. 명세는 Spec Kit 중심으로 유지하되 구현 기술 스택은 과제와 기존 환경에 맞춘다.

## 먼저 확인할 경계

이 자료는 시험 허가를 제공하지 않는다. [응시 경계](references/exam-boundaries.md)를 처음 적용할 때 읽고, 최신 과제·운영 안내와 기존 프로젝트 지침을 우선한다. 시험 중 이 저장소 반입이 허용되는지 확인되지 않았다면 준비·리허설 자료로만 사용한다. AI 금지 서술형 단계라면 답안 작성·분석·검토를 수행하지 않는다.

## 호출하면 먼저 진행할 작업

설치는 실행이 아니다. 허용된 개발 과제에서 이 Skill을 호출하면 아래 준비를 별도 승인 질문 없이 진행한다. 이 저장소 자체를 유지보수하는 작업이나 단순 설명 요청에는 과제용 파일을 생성하지 않는다.

1. **역할부터 구분한다.** 작업 요청 파일을 전달받은 보조 세션은 그 요청만 수행하고 2~6의 메인 절차를 건너뛴다. 메인으로 다시 초기화하거나 다른 세션을 재귀적으로 배정하지 않는다.
2. 메인은 README·기존 지침·실행 환경과 현재 Spec Kit 문서를 확인한다. Spec Kit을 명세·계획·작업의 기본 흐름으로 사용하되 실제 설치본의 명령만 호출한다. 없으면 설치를 기다리지 않고 같은 기준의 간결한 문서로 진행하며 사용했다고 주장하지 않는다.
3. [Bash 세션 운영](references/bash-sessions.md)을 읽고 `python3 <Skill 절대경로>/scripts/bootstrap_parallel.py --project-root <프로젝트 절대경로>`로 초기화한다. 경로는 모두 실제 위치로 바꾼다. `.cofa/`의 배정표·양식·시작 프롬프트만 생성하며 기존 파일은 보존한다. Python이 없으면 같은 최소 문서를 직접 작성한다.
4. 기존 Spec Kit 명세·계획·작업 목록의 실제 경로를 `.cofa/coordination.md`에 연결한다. 별도 명세를 복제하지 않는다. 메인은 첫 실행 흐름과 독립 작업을 정하고, 실제 입력·유일한 담당·수정 소유권·완료 기준·보고서 경로를 채운 첫 요청을 `.cofa/tasks/R01.md`에 작성한다. 기존 배정이 있으면 먼저 상태와 담당을 확인해 재개하고, 새 배정은 다른 ID·회차로 작성한다. 실행 상태는 배정표 한 곳에서 관리하고, 보조 시작 프롬프트의 작업 경로와 담당 별칭을 실제 배정에 맞게 채운다. 초기에는 원문 대비 요구사항 검토를 우선하고, 계약이 정해진 독립 구현은 구현 작업으로 배정한다.
5. 사용자에게 **열 Bash 수, 제공 Codex 실행 방법(확인된 경우), 첫 요청을 읽힐 프롬프트**를 한 번에 제시한다. 별도 Bash의 동일 파일 접근·독립 세션·동시 실행은 실측 전까지 미확인으로 기록한다. 사용자가 탭을 열고 세션을 시작하는 동안 메인은 독립 작업을 계속한다.
6. 공유 파일·동시 실행이 확인되면 배정한 범위만 병렬로 진행한다. 파일별 수정 책임자와 선행 계약을 지키고, 회차별 결과를 직접 검토한 뒤 통합한다. 지원되지 않으면 같은 작업을 순차 수행한다. 터미널 자동 생성, 세션 간 대화 공유, 파일 잠금, 보조 프로세스 자동 실행은 가정하지 않는다.

`cofa-delivery` 폴더 하나에 이 준비에 필요한 스크립트·양식·운영 지침이 포함된다. 다른 Skill이나 MCP는 선택 사항이다. 과제 파일은 제공 작업 공간에 두고 이 공개 준비 저장소에는 만들지 않는다.

## 유지할 기준

- 원문 요구와 해석·가정을 구분한다. 자료에 이미 답이 있는 질문은 반복하지 않는다.
- 결과를 바꾸는 업무 조건은 확인한다. 통상적인 구현 선택은 범위 안에서 진행한다.
- 완료 기준을 관찰 가능한 동작으로 정하고 구현 위치·검증 증거와 연결한다.
- 현재 환경을 먼저 실행한다. 가장 중요한 사용자 흐름을 끝까지 완성한 뒤 확장한다.
- Spec Kit을 기준 문서의 기본 도구로 사용한다. 다른 계획 프레임워크의 전체 절차를 병행하지 않고, 검토 결과는 같은 명세와 작업 목록에 반영한다.
- 초기에는 핵심 요구·첫 완료 기준과 가정을 정해 구현을 시작하고, 첫 흐름·핵심 로직 변경·제출 전 필요한 코드 투어만 갱신한다. 180분 과제의 초기 계획 20~30분은 권장 목표이며 공식 제한이 아니다.
- 에이전트의 완료 보고는 증거가 아니다. 관련 검사 결과와 실제 동작을 확인한다.
- 결정 이유, 실패와 수정, 남은 한계를 간결하게 남긴다. 기록이나 성공 수치를 꾸미지 않는다.

필요한 경우에만 [자산 템플릿](assets/)을 과제 작업 공간에 맞춰 사용한다. 기존 파일을 덮어쓰지 않으며, 과제에서 지정한 제출 파일이 우선이다.

별도 Skill 폴더가 설치되지 않았다면 있다고 가정하지 말고 기존 문제 정의·설계·검증 참조로 진행한다. 명세 도구와 별도의 상충하는 계획 문서를 중복 생성하지 않는다.
