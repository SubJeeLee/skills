# Docker 빌드와 실행 경계 점검

Dockerfile 작성, 이미지 빌드, 컨테이너 실행, 기능 검증, 외부 배포는 서로 다른 완료 상태다. 원문의 요구 범위와 실행 환경을 먼저 확인한다. 파일만 작성했다면 빌드 성공·기동 성공·배포 완료라고 기록하지 않는다. 실제 배포를 요구하지 않는 과제에 클라우드·레지스트리 업로드를 추가하지 않는다.

## 그림에 연결할 항목

| 항목 | 코드·설정과 대조할 내용 |
| --- | --- |
| 빌드 컨텍스트 | 빌드 명령의 경로, COPY 대상이 컨텍스트에 포함되는지, .dockerignore 제외와 필수 파일 누락 |
| 의존성 | 실제 런타임·잠금 파일·설치 명령, 개발 환경에만 있는 전역 패키지에 의존하는지 |
| 빌드 산출물 | RUN 단계에서 무엇을 만들고 런타임 이미지에 어떤 파일을 가져오는지 |
| 단계 구성 | 다단계가 필요한 근거가 있는지. 단순 앱에 다단계를 강제하지 않음 |
| 시작 프로세스 | WORKDIR, CMD·ENTRYPOINT, 실제 파일·실행 명령과 종료·오류 처리 |
| 네트워크 | 앱 수신 주소·컨테이너 내부 포트·호스트 매핑 또는 플랫폼 미리보기 경로의 구분 |
| 데이터 | 이미지에 복사한 초기 파일, 실행 중 쓰기 경로, 볼륨·외부 DB가 실제로 있는지와 재시작 시 유지 범위 |
| 구성·비밀정보 | 빌드 시점과 실행 시점 설정 구분, 실제 비밀값을 이미지·다이어그램·로그에 포함하지 않음 |
| 검사 | 빌드·기동·핵심 요청을 각각 실제로 실행했는지와 결과·실패 이유 |

`EXPOSE`는 포트 설명이며 호스트로 포트를 자동 공개하지 않는다. 컨테이너 내부 `localhost`와 다른 컨테이너·호스트 주소를 혼동하지 않는다. DB 준비가 필요한 앱에서 프로세스 시작 순서만으로 연결 준비가 완료됐다고 가정하지 않는다.

## 검증 수준 기록

1. 정적 검토: 파일·경로·명령·포트의 일치 여부를 코드로 확인.
2. 이미지 빌드: 허용된 Docker 데몬이 있을 때 실제 명령과 결과를 기록.
3. 컨테이너 기동: 실제 프로세스·로그·포트 접근을 확인.
4. 핵심 기능: 컨테이너에서 대표 요청과 실패 조건을 확인. 지속성이 요구될 때는 재시작·재조회도 확인.

환경이 지원하지 않는 단계는 실행 불가·미검증으로 남기고 원인을 기록한다. 호스트에서 성공한 테스트를 컨테이너 검증으로 대체 표기하지 않는다. 기존 Dockerfile을 읽고 평가하되 이 문서의 체크 목록을 맞추기 위해 불필요한 Compose·DB·헬스체크 서비스를 추가하지 않는다.
